# Hero image origin policy

Fund-a-Farm keeps its eight editable fields and current component version. Its hero image accepts safe internal paths or credential-free HTTPS URLs whose exact origin matches the configured `VITE_CORE_PLATFORM_ADMIN_ORIGIN`. Matching includes the port: suffix matches, other ports, userinfo, HTTP, backslashes and control characters are rejected. This image policy does not restrict CTA destinations.

Core's additive manifest image field policy is `allowedImageOrigins`, an optional unique list of at most eight canonical exact HTTPS origins. It is invalid on non-image fields. An empty list permits only internal paths. Omission preserves legacy manifests' existing HTTPS image behavior. The Better Farms example hero field explicitly names `https://dashboard.better-farms.example`, matching that manifest's admin origin. The deployed manifest must name the real configured Core admin origin. No wildcard or generic `https:` CSP allowance is added.

The site uses the same shared image-origin validator to construct the production `img-src` directive: self, data, and the one validated Core HTTPS origin. Unconfigured or malformed origin permits only internal content images. Preview's existing loopback HTTP exception remains a preview-only capability; it does not authorize external HTTP hero images. Core-hosted relative `/r2/...` images must be supplied as absolute URLs at the Core origin when used on the separate site; relative image paths always refer to the site itself.

Deployment validation must establish agreement among the manifest image allowlist, the site's build-time `VITE_CORE_PLATFORM_ADMIN_ORIGIN`, and its runtime value. Client configuration is embedded by Vite, while the server reads runtime configuration. A runtime origin change requires rebuilding the client. There is no automatic startup comparison with a persisted build manifest in this slice. A mismatch fails closed through validation/CSP intersection and can make an otherwise approved hero fail to render; it is not successful integration. Tests cover this disagreement explicitly.

Deploy Core's policy-aware validator before a manifest containing the new property: old strict manifest readers reject unknown fields. The unchanged schema/component version is additive only for upgraded validators; it does not imply compatibility with previously deployed strict readers. Do not enable the explicit site policy with content from an arbitrary external CDN that was previously accepted by legacy validation. Review/update existing hero content first.

This allows images served directly by the configured Core HTTPS origin. Separate R2 public/CDN hostnames are not automatically trusted; they require a separately approved policy change. No media import, provider configuration, production action, or expansion of editable fields is included.
